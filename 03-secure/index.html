    03 — Secure agents (Tetragon + Agent Sandbox)¶

    An AI agent is, by design, given tools and told to act. That is exactly what makes it useful — and exactly what makes it risky. A prompt-injected or mis-behaving agent will happily run whatever tool it can reach. This module adds two independent layers of defence that were installed in module 01:

    • Agent Sandbox — contain where an agent can go (namespace isolation).
    • Tetragon — observe and optionally enforce what an agent's processes do at runtime (eBPF).

    Defence in depth

    Neither layer replaces the other. The sandbox is a static boundary (admission + network policy); Tetragon is a runtime sensor that sees the actual syscalls/exec/network events — and can kill on policy violation. Use both.

    Part A — Agent Sandbox (isolation baseline)¶

    The agent-sandbox namespace ships a self-contained isolation baseline — no external project required. It lives in cluster/agent-sandbox/isolation.yaml and enforces two things on anything scheduled into it:

    Control What it does
    Pod Security Admission restricted Pods must run non-root, drop ALL Linux capabilities, forbid privilege escalation, and use the RuntimeDefault seccomp profile.
    Default-deny NetworkPolicy All ingress is blocked; egress is allowed only to DNS (port 53) and the OTel gateway (4317/4318) — so a sandboxed agent can still be observed but cannot roam the cluster or call out to the internet.

    Verify the sandbox¶

    # PSA labels enforce the "restricted" profile
kubectl get ns agent-sandbox -o jsonpath='{.metadata.labels}'; echo

# the default-deny policy is present
kubectl -n agent-sandbox get networkpolicy

    You should see pod-security.kubernetes.io/enforce: restricted in the labels and a default-deny-all NetworkPolicy.

    Prove it actually blocks¶

    Try to schedule a privileged, root pod into the sandbox — admission must reject it:

    kubectl -n agent-sandbox run rogue --image=busybox:1.36 --restart=Never \
  --overrides='{"spec":{"containers":[{"name":"rogue","image":"busybox:1.36","securityContext":{"privileged":true,"runAsUser":0},"command":["sleep","3600"]}]}}' \
  --command -- sleep 3600

    Expected

    The API server refuses the pod with a violates PodSecurity "restricted" error (privileged, runAsUser=0, missing seccomp, capabilities not dropped). That's admission control doing its job — the rogue workload never starts.

    Now prove the network boundary from a compliant pod:

    # a compliant (non-root, no caps) pod lands, but egress is denied except DNS + OTel
kubectl -n agent-sandbox run probe --image=curlimages/curl:8.10.1 --restart=Never \
  --overrides='{"spec":{"containers":[{"name":"probe","image":"curlimages/curl:8.10.1","securityContext":{"allowPrivilegeEscalation":false,"runAsNonRoot":true,"runAsUser":65534,"capabilities":{"drop":["ALL"]},"seccompProfile":{"type":"RuntimeDefault"}},"command":["sleep","120"]}]}}' \
  --command -- sleep 120

kubectl -n agent-sandbox exec probe -- curl -s -m 5 https://example.com || echo "BLOCKED (expected)"
kubectl -n agent-sandbox delete pod probe rogue --ignore-not-found

    The external curl times out → the default-deny egress policy is working.

    Stronger isolation later

    The baseline is PSA + NetworkPolicy, which needs no extra controller. For runtime-level isolation (gVisor/Kata-backed pods) you can layer on kagent substrate or kubernetes-sigs/agent-sandbox — both are additive and don't remove this baseline. See cluster/agent-sandbox/README.md.

    Part B — Tetragon (eBPF runtime security)¶

    Tetragon attaches eBPF programs to the kernel to observe — and optionally enforce — process execution and network behaviour, with almost no overhead. It was installed as a DaemonSet in module 01 (cluster/tetragon/).

    Verify Tetragon is running¶

    kubectl -n tetragon get pods            # tetragon DaemonSet + tetragon-operator Ready

    Watch what your agents actually do¶

    Stream live process/network events with the tetra CLI that ships inside the DaemonSet pod. Leave this running in one terminal, then send a prompt to the SRE agent (module 02) in another:

    kubectl -n tetragon exec ds/tetragon -c tetragon -- \
  tetra getevents -o compact

    You'll see a line for every process_exec and network connection across the node — including the processes the kagent agents spawn when they run a tool. This is your ground-truth audit log: what did the agent's container actually execute?

    Filter to the interesting bits

    tetra getevents -o compact --pods <pod> narrows the stream to a single pod. Pipe to grep for a specific binary (e.g. grep curl) to catch an agent reaching for the network.

    Optional: enforce, don't just observe¶

    Tetragon can turn an observation into a kill. A TracingPolicy can, for example, Sigkill any process in the sandbox that tries to execute an unexpected binary. This is powerful but kernel-dependent on a shared Codespace host — see the troubleshooting note below before relying on enforcement.

    # Illustrative — a policy that kills shells spawned inside the sandbox namespace.
apiVersion: cilium.io/v1alpha1
kind: TracingPolicyNamespaced
metadata:
  name: no-shell-in-sandbox
  namespace: agent-sandbox
spec:
  kprobes:
    - call: "sys_execve"
      syscall: true
      args:
        - index: 0
          type: "string"
      selectors:
        - matchArgs:
            - index: 0
              operator: "Postfix"
              values: ["/bin/sh", "/bin/bash"]
          matchActions:
            - action: Sigkill

    eBPF on a Codespace kernel

    k3d/kind nodes share the Codespace host kernel. Observation (getevents) works on most hosts; enforcement (Sigkill) may be unavailable on a restricted host kernel. If Tetragon pods CrashLoop, see Troubleshooting → Tetragon.

    What you achieved (acceptance)¶

    • The agent-sandbox namespace rejects privileged/root pods and blocks egress except DNS + telemetry.
    • Tetragon streams real exec/network events from your running agents, giving you a runtime audit trail (and an optional enforcement hook).

    Your agents can now act — but only inside a box you drew, under a sensor that watches. Next: 04 — Observe with Dynatrace to see cost and performance of every agent run.
